## 0. 面试 60 秒开场白（先背这段）

> 「我独立完成了一个 Git 命令行可视化教学应用。技术栈是 React 19 + TypeScript + Vite，用 Vitest 做单元测试，GitHub Actions 自动构建并部署到 Pages。
>

> 整个项目有 25 关课程体系、进度持久化、ErrorBoundary 容错，引擎层单测覆盖了图可达性、merge/rebase/reset 等语义。」

## 3. TypeScript 深度用法（面试必讲）

### 3.1 可辨识联合（Discriminated Union）建模命令

`src/engine/types.ts` 里把 Git 命令解析成带 `type` 字段的联合类型：

```ts
export type ParsedCommand =
  | { type: 'commit'; message: string }
  | { type: 'merge'; name: string }
  | { type: 'reset'; mode: ResetMode; steps: number }
  | { type: 'switch'; name: string; create: boolean }
  | { type: 'unknown'; raw: string; hint: string }
  // ... 20+ 种
```

处理时 TypeScript 自动收窄（narrowing）：

```ts
function handle(cmd: ParsedCommand) {
  switch (cmd.type) {
    case 'commit':
      // 这里 cmd.message 类型安全，不存在 undefined
      return doCommit(cmd.message);
    case 'merge':
      return doMerge(cmd.name);
  }
}
```

**面试追问：为什么不用 if-else 判断字符串？**
答：可辨识联合让编译器穷尽检查（exhaustive check）。漏处理一个分支会编译报错，比运行时 `unknown command` 更早暴露。Java 里等价方案是 sealed interface + pattern matching（Java 17+）。

### 3.2 接口建模领域对象

```ts
interface Commit {
  id: CommitId;
  parents: CommitId[];   // 支持 merge 双父
  message: string;
  createdAt: number;
}

type Head =
  | { kind: 'branch'; name: string }
  | { kind: 'detached'; commitId: CommitId };
```

`Head` 也是联合类型：HEAD 要么在分支上，要么 detached，不可能同时是两者。

### 3.3 不可变更新 + 结构化克隆

```ts
function cloneState(state: RepoState): RepoState {
  return {
    commits: Object.fromEntries(
      Object.entries(state.commits).map(([k, v]) => [k, { ...v, parents: [...v.parents] }]),
    ),
    branches: { ...state.branches },
    // ...
  };
}
```

**面试怎么讲：** 「状态更新是 copy-on-write：先深拷贝一份，改完返回新对象。React 的 `setState` 依赖引用比较，不可变更新让 `useMemo` / `React.memo` 能正确跳过重渲染。」

**Java 对照：** 类似 Java 的不可变对象 / Builder，或函数式里 `withXxx()` 返回新实例。

### 3.4 工程配置要点

`tsconfig` 严格模式；`package.json` 的 `"build": "tsc -b && vite build"` 先类型检查再打包——类型错误会阻断部署。

## 4. React 状态管理（不用 Redux 的理由）

### 4.1 状态在哪里

`App.tsx` 用一组 `useState` 管理应用状态：

| 状态 | 含义 |
|------|------|
| `world` | 核心：多用户 Git 世界快照 |
| `progress` | 关卡完成度 + 技能档 |
| `termByUser` | 终端输出（Alice/Bob 各一份） |
| `explanation` | 右侧「刚刚发生了什么」 |
| `highlights` | 图上高亮（新建 commit、移动的分支等） |
| `checkResult` | 通关判定结果 |

### 4.2 Hooks 使用模式

```ts
const [world, setWorld] = useState(() => bootWorld(...));  // 惰性初始化

const run = useCallback((raw: string) => {
  const result = applyWorldCommand(world, raw);
  setWorld(result.world);           // 不可变新状态
  setExplanation(result.explanation);
  setHighlights(result.highlights);
}, [world]);

const level = useMemo(
  () => getLevel(progress.currentLevelId),
  [progress.currentLevelId],
);
```

**面试常问：`useCallback` / `useMemo` 什么时候用？**
- `useMemo`：昂贵计算或需要稳定引用的派生数据（如 `getLevel`、图布局）
- `useCallback`：传给子组件的回调，避免子组件无意义重渲染
- 不要无脑包：简单值直接算，包了反而多一次依赖比较

### 4.3 副作用与持久化

```ts
useEffect(() => {
  saveProgress(progress);
}, [progress]);
```

`loadProgress` / `saveProgress` 封装 localStorage，带 try/catch 和旧版本 key 迁移（`git-instructor:progress` → `git-instructor:progress:v2`，并做 level id 映射）。

**面试怎么讲数据迁移：** 「关卡目录重排后 id 变了，我在读取旧数据时跑一遍 `LEGACY_LEVEL_IDS` 映射，读完立即写回新 key。兼容线上已有用户进度。」

### 4.4 ErrorBoundary

React 错误边界（class component，这是 React 里唯一仍需要 class 的场景）：子树渲染抛错时降级 UI，并提供「清除本地进度」自救按钮。

**面试加分：** 「React 16+ 的 ErrorBoundary 只能捕获渲染期错误，不能捕获事件回调里的异步错误——所以引擎层用 Result 风格返回 `{ ok: boolean }`，而不是 throw。」

## 5. 可视化：自研 SVG 提交图布局

### 5.1 问题

Git 提交历史是 **有向无环图（DAG）**，要画成：

- 每个 commit 一个节点，按时间从新到旧纵向排列
- 同一开发线的提交在同一「泳道」（lane），分支岔开时开新泳道
- merge 提交有双父边（两条入边）
- 分支标签、HEAD 指针、远程 `origin/*` 引用分列展示

### 5.2 算法思路（`layout.ts`）

1. **可达性裁剪**：从所有分支 tip + HEAD 做 DFS/BFS，只画能到达的提交
2. **泳道分配**：沿每个分支的 first-parent 链分配 lane index
3. **坐标计算**：
   - `y = PAD_TOP + index * NODE_GAP_Y`（新提交在上）
   - `x = RAIL_X + lane * LANE_GAP_X`
4. **文字列避让**：hash 列、说明列、HEAD 列、远程列用固定常量排版，说明按像素宽度截断（CJK 全角算 13px，半角 7.5px）

### 5.3 图着色

```ts
export function colorForBranch(name: string): string {
  if (name === 'main') return LANE_COLORS[0]; // 绿色固定给 main
  let h = 0;
  for (let i = 0; i < name.length; i++) {
    h = (h * 31 + name.charCodeAt(i)) >>> 0; // 稳定哈希
  }
  return LANE_COLORS[1 + (h % (LANE_COLORS.length - 1))];
}
```

**面试亮点：** 分支名 → 颜色是确定性哈希，不依赖插入顺序。删掉 feature-a 不会让 feature-b 换色——UI 稳定性细节。

### 5.4 面试怎么讲

> 「提交图不是通用图表，所以没上 ECharts/G6。我自研了泳道布局：先从分支 tip 做可达性遍历裁剪节点，再沿 first-parent 链分配泳道，最后算坐标并处理中文文本宽度。merge 边、远程引用列、HEAD 闪烁高亮都是领域定制。」

**Java 对照：** 这是图算法 + 纯计算层，类似后端的报表/拓扑服务。`layout` 函数签名就是 `RepoState → GraphLayout`，可独立压测。

## 6. 命令解析器（Parser）

### 6.1 两阶段

```
输入字符串 → tokenize() → tokens[] → parseCommand() → ParsedCommand
```

`tokenize` 支持单双引号和转义：

```ts
git commit -m "fix: 修复登录 bug"
// → ['commit', '-m', 'fix: 修复登录 bug']
```

### 6.2 错误不抛异常

解析失败返回：

```ts
{ type: 'unknown', raw, hint: '请使用 git commit -m "提交说明"' }
```

UI 拿 `hint` 显示中文提示。**Result 优于 Exception**——对用户输入的容错是产品需求，不是异常路径。

**Java 对照：** 类似用 Optional / Either 做校验，而不是用异常控制业务流。

## 7. 多用户协作模拟（WorldState）

```ts
interface WorldState {
  activeUser: 'alice' | 'bob';
  users: Record<UserId, RepoState>;          // 两份本地仓库
  remoteBranches: Record<string, CommitId>;  // 共享远程
  remoteCommits: Record<CommitId, Commit>;
}
```

语义要点（`world.ts` / 单测里验证过）：

| 行为 | 模拟语义 |
|------|---------|
| Alice commit | 只改 Alice 的 `RepoState`，Bob 看不到 |
| `git push` | 把 Alice tip 写入 `remoteBranches`，对象进 `remoteCommits` |
| `git fetch` | 把远程 commit 拷进本地，**不**动本地分支 |
| `git pull` | fetch + 合并到当前分支 |
| 非快进 push | 返回 `ok: false`，stderr 含 `non-fast-forward` |
| `git clone` | 从 `remoteCommits` 拷贝可达对象到本地 |

**面试怎么讲：** 「我用双本地仓库 + 一份共享远程，把分布式版本控制的核心不变量（本地不可见性、fetch 不合并、push 快进约束）写成单测锁死。」

```ts
// world.test.ts 节选
it('alice commits are not visible to bob until fetch/pull', () => { ... });
it('rejects non-fast-forward push', () => { ... });
it('fetch imports remote commits without merging', () => { ... });
```

```ts
interface LevelDef {
  id: number;
  stageId: string;
  title: string;
  startWorld: () => WorldState;          // 工厂函数：每关初始世界不同
  check: (ctx: LevelCheckCtx) => LevelCheckResult;  // 通关谓词

```

设计模式：

1. **策略/谓词模式**：每关的 `check` 是纯函数，比较 `before`/`after` 世界状态

**面试怎么讲：** 「关卡是数据 + 策略函数，不是 if-else 页面。新增一关只需要在 catalog 里加一个对象，UI 和引擎零改动。」

### 10.2 GitHub Actions 部署

```yaml
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm          # 依赖缓存，加速构建
      - run: npm ci           # 锁文件安装，可复现
      - run: npm run build
      - uses: actions/upload-pages-artifact@v3
  deploy:
    needs: build
    environment: github-pages
    steps:
      - uses: actions/deploy-pages@v4
```

**面试要点：**

1. `npm ci` vs `npm install`：CI 用 `ci` 严格按 lock 装，保证可复现（类比 Maven 锁版本）
2. `cache: npm`：缓存 `~/.npm`，二次构建快
3. `needs: build`：build → deploy 两阶段，build 失败不部署
4. `concurrency: group: pages`：防止并发部署互相覆盖
5. 权限最小化：`contents: read` + `pages: write` + `id-token: write`

### 10.3 Vite 双 base 路径

```ts
base: command === 'build' ? '/Git-Instructor/' : '/',
```

开发用 `/`，生产 GitHub Pages 项目页需要子路径。**面试小细节：** 体现你知道静态托管的 base path 问题。

## 12. 面试高频追问 Q&A

**Q1：为什么不用 Redux？**
> 应用状态是一棵树，变更入口集中在「执行一条命令」这一个 reducer。`useState` + 纯函数 apply 已足够，上 Redux 会多样板代码而无收益。如果以后要接多人在线协作或时间旅行调试，再考虑规范化 store。

**Q2：React 19 有什么你实际用到的变化？**
> 本项目主要还是函数组件 + Hooks。19 的方向是 Server Components / Actions——纯客户端教学沙箱用不到 SSR。选 19 是跟随稳定版，类型定义 `@types/react` 也是配套的。

**Q3：性能优化做了什么？**
> 1. 引擎层纯计算，无 IO，本身快
> 2. `useMemo` 缓存关卡查询和图布局（布局依赖 state 引用，不可变更新保证不失效）
> 3. 分支色哈希稳定，避免无关重绘换色
> 4. 文本按像素截断，避免 SVG 过度重排

**Q4：如何保证 Git 模拟的正确性？**
> 不追求 100% 兼容真实 Git，而是**教学用语义不变量**单测锁定：不可达提交裁剪、merge 双父、reset 三模式对工作区/暂存区的影响、非快进 push 拒绝。与真实 Git 的差异写在讲解栏。

**Q5：TypeScript 相比 Java 泛型/封装的优势？**
> 1. 联合类型 + 类型收窄，比 Java 的继承体系更轻
> 2. 结构化类型（duck typing），接口不用 `implements`
> 3. 编译到 JS 无运行时类型擦除问题；但运行时无校验，边界处（localStorage、用户输入）要自己 parse/validate——这点和 Java 反序列化校验一样。

**Q6：项目里最难的 bug？**
> （按你的实际经历替换）可以讲：
> - 多分支布局时文字列与 HEAD 签重叠 → 改成固定列 + 像素级截断
> - localStorage 旧关卡 id 乱序 → 写迁移表并在 load 时回写
> - Alice/Bob 状态共享引用导致串仓库 → 深拷贝 `cloneRepoState`

**Q7：如果没有后端，怎么体现工程能力？**
> 引擎即「领域服务」，测试、类型、CI、可扩展关卡架构都是后端工程能力的平移。面试官若要全栈，可以顺势聊「若要加用户系统 / 云端进度，我会加 NestJS + Postgres，引擎包抽成共享库」。

## 13. 项目地图（面试被问「代码怎么组织」）

```
src/
  engine/          # ★ 纯业务：parse / apply / world / layout / hash
  levels/          # 课程：catalog / checks / progress / stages
  components/      # UI：TerminalPanel / CommitGraph / LevelPanel ...
  data/            # 静态数据：cheatsheet
  App.tsx          # 状态编排、模式切换
  main.tsx         # 入口 + ErrorBoundary
.github/workflows/deploy.yml   # CI/CD
docs/              # PRD + 实现规格
```

**回答套路：** 「engine 与 UI 分离；levels 是数据驱动的课程；components 只做展示；状态上收到 App。」

## 14. 30 秒 / 3 分钟 / 10 分钟三套讲法

### 30 秒（电梯稿）
> React + TypeScript 做的 Git 可视化教学应用。引擎是纯函数状态机，SVG 自研提交图布局，Vitest 锁语义，GitHub Actions 部署 Pages。适合讲类型系统、图算法、测试与 CI。

### 3 分钟（项目面）
开场白（§0）→ 架构图（§2）→ 挑两个难点（命令类型安全 + 泳道布局 或 多用户协作）→ 测试与 CI（§9-10）→ 反问面试官技术栈。

### 10 分钟（深挖）
按对方兴趣展开：类型系统深挖 sealed 联合 / React 渲染与 Hooks / 图算法 / Git 领域建模 / CI 可复现构建。始终回到「不变量 + 测试 + 分层」三条主线。
