## 1. 先建立世界观

### 1.1 Java 后端 vs 前端，差别在哪

| | Java 后端 | 本项目（前端） |
|--|----------|---------------|
| 跑在哪 | 服务器 JVM | **浏览器**（Chrome/Edge） |
| 用户看什么 | JSON/HTTP 响应 | 屏幕上的按钮、输入框、图 |
| 代码语言 | Java | TypeScript → 编译成 JavaScript |
| 框架 | Spring Boot | React |
| 构建 | Maven/Gradle | Vite |
| 包管理 | pom.xml / build.gradle | package.json + npm |
| 测试 | JUnit | Vitest |
| 部署 | 发到 Linux/容器 | 发静态文件（HTML/JS/CSS）到 GitHub Pages |

**一句话：**  
前端 = 用户能看见、能点的那层。本项目**没有后端**，所有「业务逻辑」都在浏览器内存里跑。

### 1.2 浏览器里运行的是什么

浏览器能直接执行的是三样东西：

1. **HTML** — 页面结构（有什么）
2. **CSS** — 样式（长什么样）
3. **JavaScript** — 行为（点了发生什么）

浏览器**不认识** TypeScript、不认识 JSX、不认识 React。  
所以需要「编译 + 打包」：把 `.tsx` 源码编译成浏览器认识的 `.js`，这个工具链就是 **Vite**。

```
你写的 TypeScript/React 源码
        ↓  编译打包（Vite）
浏览器能执行的 HTML + JS + CSS（dist/ 目录）
```

### 1.3 本项目的技术地图（先混个脸熟）

```
开发语言     TypeScript  （Java 之于 JVM ≈ TS 之于 JS）
UI 框架      React       （组件化拼界面）
运行时       Node.js     （开发时跑工具链；不是服务器）
包管理       npm         （装依赖，类似 Maven）
构建工具     Vite        （编译 TS/JSX、启动开发服务器、打包）
测试         Vitest      （类似 JUnit）
静态检查     Oxlint      （类似 Checkstyle）
CI/CD        GitHub Actions + GitHub Pages
浏览器 API   localStorage / SVG
```

## 2. Node.js

### 2.1 是什么

**Node.js = 把 Chrome 用的 JavaScript 引擎（V8）拿出来，做成一个能在操作系统上跑的程序。**

- 没有 Node：JS 只能在浏览器网页里跑
- 有了 Node：JS 可以读写文件、跑脚本、启动开发服务器、跑测试

### 2.2 和 Java 运行时对照

| | Java | Node.js |
|--|------|---------|
| 虚拟机/引擎 | JVM | V8（Chrome 同款） |
| 语言 | Java | JavaScript |
| 装包命令 | `mvn` | `npm` |
| 跑主程序 | `java -jar app.jar` | `node xxx.js` |
| 全局装工具 | Maven 插件 | `npm install -g` |

### 2.3 本项目里 Node 干什么

**不是**用 Node 写业务服务器！只用来跑开发工具：

```bash
npm run dev     # 启动开发服务器（Vite）
npm test        # 跑 Vitest 测试
npm run build   # 编译打包
```

业务代码（React 组件、Git 引擎）最后是**打包后在浏览器里跑**的。

### 2.4 怎么验证你装好了

```bash
node -v    # 例如 v22.x
npm -v     # 例如 10.x
```

本机若装了 nvm/fnm 会更好，但只要版本 ≥ 18 一般都能跑本项目。

## 3. npm 与包管理

### 3.1 npm 是什么

**npm = Node Package Manager，前端的 Maven Central。**

- 全世界最大的开源包仓库之一
- `npm install xxx` = `mvn` 拉依赖
- 依赖声明在 `package.json`（≈ pom.xml）

### 3.2 三个核心文件

| 文件 | 作用 | Java 对照 |
|------|------|-----------|
| `package.json` | 项目元信息 + 依赖清单 + 脚本命令 | `pom.xml` |
| `package-lock.json` | **精确版本锁定**（含传递依赖树） | 更像 Gradle 的 `gradle.lockfile` |
| `node_modules/` | 依赖实际解压在这里 | `~/.m2/repository` 的项目私有拷贝 |

### 3.3 install vs ci（面试常考）

```bash
npm install     # 按 package.json 装，可能「顺手」升级 lock 里允许的版本
npm ci          # 严格按 package-lock.json 装，干净、可复现
```

**CI 里必须用 `npm ci`：**  
和你坚持 Maven 用固定版本、发布 lock 文件是同一个道理——「我机器上能跑」≠「构建机上能跑」，靠 lock 文件保证。

### 3.4 依赖分类

```json
"dependencies": {
  "react": "^19.2.8",          // 运行时需要，会打进最终产物
  "react-dom": "^19.2.8"
},
"devDependencies": {
  "vite": "^8.2.2",            // 只在开发/构建时用
  "typescript": "~6.0.2",
  "vitest": "^5.0.0"
}
```

- `dependencies`：运行时（浏览器要加载的）
- `devDependencies`：开发工具（编译器、测试、lint）

### 3.5 版本号语义（语义化版本 SemVer）

```
^19.2.8
│ │ │ │
│ │ │ └── patch  修 bug
│ │ └──── minor  加功能（向后兼容）
│ └────── major  破坏性变更
└──────── ^ 表示「major 不变，可自动升 minor/patch」
```

| 写法 | 含义 | 记忆 |
|------|------|------|
| `^19.2.8` | ≥19.2.8 且 <20.0.0 | 默认推荐 |
| `~19.2.8` | ≥19.2.8 且 <19.3.0 | 只接受 patch |
| `19.2.8`  | 只要这个版本 | 精确 |

**面试可以说：** 「前端 SemVer 和 Java 语义版本一致；我靠 package-lock 做到可复现构建，CI 用 npm ci。」

### 3.6 npm scripts（≈ Maven 插件命令）

```json
"scripts": {
  "dev": "vite",
  "build": "tsc -b && vite build",
  "test": "vitest run",
  "lint": "oxlint"
}
```

运行：

```bash
npm run dev      # 相当于执行 vite
npm run build    # 先 tsc -b 类型检查，再 vite build
npm test         # npm test 是特殊写法，不用写 run
```

**和 Maven 对照：**

| npm | Maven |
|-----|-------|
| `npm run dev` | `mvn spring-boot:run` |
| `npm run build` | `mvn package` |
| `npm test` | `mvn test` |
| `npm run lint` | `mvn checkstyle:check` |

## 4. ES Module

### 4.1 是什么

现代 JS 的官方模块系统，关键字就是 `import` / `export`（ESM）。

```ts
// engine/types.ts  —— 对外导出类型
export interface Commit { ... }

// engine/apply.ts  —— 导入使用
import type { Commit, CommandResult } from './types';
export function applyCommand(...) { ... }
```

### 4.2 和 Java 包对照

| Java | ES Module |
|------|-----------|
| `package com.xxx.engine;` | 文件所在目录即「包」 |
| `import com.xxx.engine.Commit;` | `import type { Commit } from './types';` |
| `public class` | `export function` / `export interface` |
| 默认包内可见 | 不 export 就是模块私有 |

### 4.3 两种导入风格

```ts
import { parseCommand } from './parse';   // 具名导入（常用）
import type { RepoState } from './types'; // 只导入类型（编译后擦除）
import * as engine from './engine';       // 命名空间（少用）
```

`import type` 是 TypeScript 特有：只用于类型，打包后完全消失，不影响运行时体积。

### 4.4 本项目的模块地图

```
src/engine/types.ts    领域类型（Commit, WorldState, ParsedCommand...）
src/engine/parse.ts    字符串 → 命令
src/engine/apply.ts    执行单仓命令
src/engine/world.ts    多用户/远程编排
src/engine/layout.ts   提交图布局算法
src/engine/hash.ts     可达性、祖先、回溯

src/levels/*           关卡课程数据与判定
src/components/*       React UI 组件
src/App.tsx            状态总装
```

**原则：** 引擎层不 import 任何 React 相关东西 → 可以在 Node 里单测。

## 5. TypeScript

### 5.1 是什么

**TypeScript = JavaScript + 静态类型。**  
由微软开发，编译后变成纯 JS。浏览器/Node 只跑 JS，TS 是给**人和编译器**看的。

```
你写 .ts / .tsx  →  tsc（或 Vite 内置）检查类型并降级  →  .js
```

### 5.2 为什么要类型（Java 开发秒懂）

你在 Java 里离不开：

```java
public Result apply(String cmd) { ... }
```

没有类型时 JS 会怎样：

```js
apply(42)        // 运行时才发现
apply()          // undefined 进去，深层错误
apply("git")     // 碰巧能跑，改了实现就炸
```

TS 在**写代码时 / 构建时**就报错，而不是等用户点出来。

### 5.3 和 Java 类型对照表

| 概念 | Java | TypeScript |
|------|------|-----------|
| 别名 | 没有（或包装类） | `type CommitId = string;` |
| 接口 | `interface`（可多实现） | `interface`（结构化，duck typing） |
| 枚举 | `enum` | `type ResetMode = 'soft'\|'mixed'\|'hard';` |
| 泛型 | `List<T>` | `Record<K, V>`, `Array<T>`, `Map` |
| 密封类 | `sealed interface`（17+） | 联合类型 + 字面量 |
| 空安全 | 显式 Optional/null | `?` 可选、`!` 断言、严格 null |
| 编译产物 | 字节码 | JavaScript |
| 运行时类型 | 有（反射、instanceof） | **基本没有**（类型被擦除） |

### 5.4 本项目最核心的 TS 用法

#### （1）接口建模领域

```ts
export interface Commit {
  id: CommitId;
  parents: CommitId[];  // merge 有多个父提交
  message: string;
  createdAt: number;
}
```

#### （2）可辨识联合（Discriminated Union）——面试高频

```ts
export type Head =
  | { kind: 'branch'; name: string }
  | { kind: 'detached'; commitId: CommitId };

export type ParsedCommand =
  | { type: 'commit'; message: string }
  | { type: 'merge'; name: string }
  | { type: 'reset'; mode: ResetMode; steps: number }
  | { type: 'unknown'; raw: string; hint: string }
  // ... 还有 20 种
```

**运行时**就是一个普通对象：`{ type: 'commit', message: 'hello' }`  
**编译时**靠 `type` 字段收窄：

```ts
function run(cmd: ParsedCommand) {
  switch (cmd.type) {
    case 'commit':
      // 这里 cmd 的类型自动变成 { type: 'commit'; message: string }
      return doCommit(cmd.message);
    case 'merge':
      return doMerge(cmd.name);
    case 'unknown':
      return showHint(cmd.hint);
  }
}
```

**为什么比 if-else 字符串强：**

```js
// 脆弱：写错字符串、漏分支，运行时才炸
if (cmd === 'comit') { ... }
```

```ts
// 编译器帮你看：漏了 case 可配置 exhaustive check 报错
```

**Java 17 对照：**

```java
sealed interface ParsedCommand {}
record CommitCmd(String message) implements ParsedCommand {}
record MergeCmd(String name) implements ParsedCommand {}

// switch 模式匹配
switch (cmd) {
  case CommitCmd c -> doCommit(c.message());
  case MergeCmd m  -> doMerge(m.name());
}
```

思想一模一样：**把「命令」变成类型，而不是散落的字符串。**

#### （3）Record 与映射类型

```ts
commits: Record<CommitId, Commit>;   // Map<String, Commit>
branches: Record<string, CommitId>;  // Map<String, String>
users: Record<UserId, RepoState>;    // 枚举 key 的 Map
```

#### （4）不可变更新的类型辅助

```ts
function cloneState(state: RepoState): RepoState {
  return {
    ...state,                         // 展开
    commits: Object.fromEntries(...), // 新对象
    parents: [...v.parents],          // 新数组
  };
}
```

TS 不强制不可变，但配合 React 必须习惯「改状态 = 返回新对象」。

#### （5）tsconfig（本项目）

`tsconfig.json` 是 TS 的配置，类似 Java 的 `--release` / 编译选项。  
构建命令：

```json
"build": "tsc -b && vite build"
```

**含义：先全量类型检查，过了再打包。类型错误会挡住部署。**

### 5.5 TS 的局限（面试别说满）

- 运行时没有类型：`JSON.parse` 出来的仍然是 `any`，要自己校验
- 类型再好也可能 `as` 断言逃逸
- 不能替代单测（类型检查的是「形状」，不是「业务语义」）

## 6. React

### 6.1 解决什么问题

原生 JS 写界面：

```js
document.getElementById('btn').addEventListener('click', () => {
  const el = document.createElement('div');
  el.textContent = 'hello';
  document.body.appendChild(el);
  // 状态一多，DOM 与数据对不上，极难维护
});
```

**React 思想：UI 是状态的函数。**  
`视图 = f(状态)`。状态变了，React 算出差异，自动更新 DOM。

### 6.2 组件（Component）

组件 = 一段可复用的、返回界面的函数。

```tsx
// components/TerminalPanel.tsx
function TerminalPanel({ lines, onSubmit }: Props) {
  return (
    <div className="terminal">
      {lines.map(l => <div>{l.text}</div>)}
      <input onKeyDown={...} />
    </div>
  );
}
```

| 概念 | React | Java/Spring 对照 |
|------|-------|-----------------|
| 组件 | `function X()` | Controller 方法 / 视图片段 |
| Props | 父传子的参数 | 方法参数 / Request DTO |
| 本质 | 纯展示 + 本地状态 | View 层 |

JSX 不是 HTML，是 `React.createElement` 的语法糖：

```tsx
<div className="x">hi</div>
// 等价于
React.createElement('div', { className: 'x' }, 'hi')
```

注意：JSX 里 `class` 要写成 `className`（因为 `class` 是 JS 关键字）。

### 6.3 Hooks：函数组件里用「状态」和「副作用」

React 16.8 之后主流写法是函数组件 + Hooks。本项目全是这种写法。

#### useState —— 状态

```tsx
const [input, setInput] = useState('');
// input   当前值
// setInput 更新函数（传新值，或函数式更新）
```

**类比：** 实例字段，但修改必须用 setter，React 才知道要重渲染。

**惰性初始化**（本项目常用）：

```tsx
const [progress, setProgress] = useState(() => loadProgress());
// 传函数 = 首次渲染才执行，之后忽略
```

#### useEffect —— 副作用

```tsx
useEffect(() => {
  saveProgress(progress);   // 状态变了，写入 localStorage
}, [progress]);             // 依赖数组：progress 变了才执行
```

| 依赖写法 | 含义 |
|---------|------|
| `[]` | 只在挂载时跑一次（≈ `@PostConstruct`） |
| `[a, b]` | a 或 b 变了才跑 |
| 不写 | 每次渲染都跑（少用） |

**和 Java 对照：** 副作用（存库、打日志、订阅）不要写在渲染函数体里，放进 `useEffect`，让「渲染」保持纯。

#### useMemo —— 缓存计算结果

```tsx
const layout = useMemo(
  () => layoutGraph(state),
  [state],   // state 引用变了才重算
);
```

**何时用：** 计算贵，或需要稳定引用传给子组件。  
**何时不用：** 小计算直接算，套 useMemo 反而有依赖比较成本。

#### useCallback —— 缓存函数本身

```tsx
const onSubmit = useCallback(() => {
  run(input);
}, [input, run]);
```

目的：子组件 `React.memo` 时不因「函数每次都新建」而重渲染。

#### useReducer —— 复杂状态（本项目没上，但要知道）

```tsx
const [state, dispatch] = useReducer(reducer, initialState);
```

当 `useState` 出现一堆 `setXxx` 耦合时改用它。  
**本项目选择：** 核心状态就一个 `world`，更新入口是 `applyWorldCommand` 纯函数，所以 `useState` 就够——不是不会 Redux，是收益不够。

### 6.4 数据流：单向

```
用户输入 "git commit -m hi"
    ↓
App.run()  调用引擎 applyWorldCommand
    ↓
得到新的 world（新对象）+ explanation
    ↓
setWorld(新 world)  // 批量更新状态
    ↓
React 重新渲染 CommitGraph / TerminalPanel
    ↓
用户看到图变了
```

**永远：** 状态往下传（props），事件往上回（回调）。  
不要子组件直接改父状态。

### 6.5 本项目的组件树

```
main.tsx
└── ErrorBoundary          # 捕获渲染错误
    └── App                # 状态中枢
        ├── TopBar         # 模式/用户切换
        ├── LevelPanel     # 左侧关卡
        ├── CommitGraph    # 中间 SVG 提交图
        ├── ExplanationPanel
        ├── TerminalPanel  # 底部终端
        └── CheatsheetPanel
```

### 6.6 为什么不引入 Redux / Next.js

| 方案 | 何时需要 | 本项目 |
|------|---------|--------|
| Redux/Zustand | 跨多层共享、时间旅行、中间件 | 状态树小、入口单一 → 不用 |
| React Router | 多页面 URL | 三种模式条件渲染 → 不用 |
| Next.js | SSR/SEO/文件路由 | 纯客户端工具类应用 → 不用 |

**面试话术：** 「我按最小复杂度选型。状态变更有单一入口（执行命令），用 useState + 纯函数 apply 足够；上 Redux 是过度设计。」

## 7. Vite

### 7.1 没有打包工具会怎样

浏览器不支持：

- `.tsx` 文件里的 JSX
- `import` 大量 npm 包的深层路径
- TypeScript 语法

所以需要 **构建工具**：编译 + 合并压缩 + 处理依赖。

### 7.2 Vite 是什么

**Vite = 下一代前端构建工具**（法语「快」）。

开发时：

- 启动**开发服务器**（本地 http，类似 `mvn spring-boot:run`）
- 利用浏览器原生 ESM，按需编译，冷启动极快
- **HMR**：改代码，浏览器局部热更新，不整页刷新

生产时：

- 调用 **esbuild/Rollup** 把代码打成 `dist/assets/index-xxx.js`
- 压缩、代码分割、处理静态资源

### 7.3 和 Java 构建对照

| | Java | Vite |
|--|------|------|
| 本地调试 | spring-boot:run | `npm run dev` |
| 编译 | javac | esbuild（或 tsc） |
| 打包 | jar/war | `dist/` 静态文件 |
| 热更新 | JRebel/Spring DevTools | HMR |

### 7.4 本项目 vite.config.ts 精讲

```ts
import react from '@vitejs/plugin-react'
import { defineConfig } from 'vitest/config'

export default defineConfig(({ command }) => ({
  plugins: [react()],                          // 处理 JSX
  base: command === 'build' ? '/Git-Instructor/' : '/',
  //  开发：根路径 /
  //  构建：GitHub Pages 项目页路径
  server: {
    host: true,            // 允许局域网/内网穿透访问
    allowedHosts: true,    // 允许任意 Host 头（调试用）
  },
  test: {                  // Vitest 配置写在同一个文件
    environment: 'node',
    include: ['src/**/*.test.ts'],
  },
}))
```

**`base` 为什么要判断：**  
GitHub Pages 上项目页 URL 是 `https://user.github.io/Git-Instructor/`，资源引用必须带前缀 `/Git-Instructor/`；本地开发用 `/` 最方便。  
**这是部署静态站的经典坑，面试可当细节加分。**

## 8. Vitest

### 8.1 是什么

**Vitest = 专为 Vite 生态设计的单元测试框架**，用起来像 Jest：

```ts
import { describe, expect, it } from 'vitest';

describe('git push', () => {
  it('rejects non-fast-forward push', () => {
    const r = applyWorldCommand(w, 'git push origin main');
    expect(r.ok).toBe(false);
    expect(r.stdout.join('\n')).toContain('non-fast-forward');
  });
});
```

### 8.2 和 JUnit 对照

| JUnit | Vitest |
|-------|--------|
| `@Test void foo()` | `it('foo', () => {...})` |
| `@Nested` | `describe('group', ...)` |
| `assertEquals(a, b)` | `expect(a).toBe(b)` / `toEqual` |
| `assertTrue` | `expect(x).toBe(true)` |
| `assertThrows` | `expect(fn).toThrow()` |
| `mvn test` | `npm test` |

### 8.3 `toBe` vs `toEqual`

```ts
expect(obj).toBe(other);    // 引用相等（== 指针）
expect(obj).toEqual(other); // 深比较（值相等）
```

测不可变状态更新时经常用 `toEqual` 比整棵树。

### 8.4 本项目测什么、怎么测

**配置：** `environment: 'node'` —— 引擎是纯逻辑，不需要浏览器 DOM。

**测试风格（world.test.ts）：**

```ts
function runAll(world: WorldState, cmds: string[]): WorldState {
  let w = world;
  for (const c of cmds) {
    const r = applyWorldCommand(w, c);
    if (!r.ok) throw new Error(...);
    w = r.world;   // 纯函数，线程安全式地串起来
  }
  return w;
}
```

这叫 **给定-当-则（Given-When-Then）**，和你写 Service 单测一样。

**覆盖的不变量（背两个进面试）：**

1. Alice 的提交在 push 前对 Bob 不可见  
2. 非快进 push 被拒绝，远程 tip 不变  

### 8.5 为什么测试文件在 src 里

```
src/engine/apply.ts
src/engine/apply.test.ts   # 同目录，改完实现立刻改测试
```

约定 `*.test.ts` 会被 Vitest 收集；打包时 Vite 不会把测试打进产物。

## 9. Oxlint / ESLint

### 9.1 是什么

**Lint = 静态检查「写得对不对、好不好」**，类似：

| 工具 | 生态 |
|------|------|
| Checkstyle / SpotBugs / Sonar | Java |
| ESLint | 传统 JS |
| **Oxlint** | 本项目（Rust 实现，更快） |

### 9.2 查什么

- 未使用变量
- 可疑写法（`==`、意外全局变量）
- 常见错误模式
- 可配风格规则（缩进、引号——项目用 `.oxlintrc.json`）

```bash
npm run lint
```

### 9.3 和 tsc 的分工（面试易混）

| | TypeScript 编译器 | Oxlint |
|--|------------------|--------|
| 查什么 | **类型**是否正确 | 代码**风格与错误模式** |
| 例子 | 传错参数类型 | 有未使用变量 |
| 阻断 build？ | 是（`tsc -b`） | 可单独跑，CI 可选用 |

**两者互补：** tsc 保证「类型对」，lint 保证「写法干净」。

## 10. GitHub Actions

### 10.1 什么是 CI/CD

- **CI（持续集成）**：每次 push 自动构建 + 测试，尽早暴露问题  
- **CD（持续部署/交付）**：通过后自动发布  

Java 圈常见 Jenkins / GitLab CI；GitHub 仓库原生方案是 **GitHub Actions**。

### 10.2 核心概念

| 概念 | 含义 | Jenkins 类比 |
|------|------|-------------|
| Workflow | 一个流水线（YAML 文件） | Pipeline |
| Job | 一个并行任务（一台 runner） | Stage |
| Step | Job 里的一步命令 | sh 指令 |
| Runner | 执行机（`ubuntu-latest`） | Agent/节点 |
| Trigger | 何时跑（`on: push`） | Webhook |
| Artifact | 构建产物上传 | 归档 jar |
| Environment | 部署环境（github-pages） | Deploy 环境 |

### 10.3 本项目 deploy.yml 逐行讲

```yaml
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]     # 只在 main 推送时触发
  workflow_dispatch:     # 允许手动点按钮触发

permissions:
  contents: read         # 读代码
  pages: write           # 写 Pages
  id-token: write        # Pages OIDC 身份

concurrency:
  group: pages           # 同组流水线排队
  cancel-in-progress: false  # 不取消进行中的，避免半成品上线

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4      # 拉代码（≈ git clone）
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm                   # 缓存 node_modules/下载缓存
      - run: npm ci                    # 可复现安装
      - run: npm run build             # 类型检查 + 打包
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist                   # 上传 dist 作为站点产物

  deploy:
    needs: build                       # build 成功才 deploy
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4 # 发布到 Pages
```

### 10.4 关键设计点（面试可展开）

1. **`npm ci` 而非 `npm install`** —— 可复现  
2. **`cache: npm`** —— 依赖缓存，二次构建更快  
3. **两阶段 Job** —— 测试/构建失败不会部署  
4. **权限最小化** —— 不能随便写 contents  
5. **concurrency group** —— 避免两次 push 部署互相踩  

### 10.5 和 Java CI 对照

| GitHub Actions | Jenkins |
|----------------|---------|
| `actions/checkout` | `git` step |
| `actions/setup-node` + cache | 工具安装 + Maven 缓存 |
| `npm ci && npm run build` | `mvn -B verify` |
| `upload-pages-artifact` | `archiveArtifacts` |
| `deploy-pages` | 部署到服务器/容器 |

## 11. localStorage

### 11.1 是什么

浏览器提供的 **键值对存储**，数据存在用户本机，刷新、关浏览器后仍在。

```ts
localStorage.setItem('key', JSON.stringify(obj));
const raw = localStorage.getItem('key');
localStorage.removeItem('key');
```

### 11.2 特性（和 Cookie / 服务器 DB 对比）

| | localStorage | Cookie | 服务端数据库 |
|--|--------------|--------|-------------|
| 存哪 | 用户浏览器 | 浏览器，每次请求可带上 | 服务器 |
| 大小 | 约 5MB/域 | 约 4KB | 无此限制 |
| 过期 | 默认永久 | 可设 | 你定 |
| 读写方 | 仅本域 JS | 本域 JS + HTTP 头 | 后端 |
| 本项目 | 保存学习进度 | 不用 | **没有后端** |

**注意：** 存的是**字符串**，对象必须 `JSON.stringify` / `JSON.parse`。敏感数据不要放。

### 11.3 本项目怎么用（含数据迁移）

```ts
const STORAGE_KEY = 'git-instructor:progress:v2';
const LEGACY_STORAGE_KEY = 'git-instructor:progress';

export function loadProgress(): LevelProgress {
  try {
    const saved = localStorage.getItem(STORAGE_KEY);
    const raw = saved ?? localStorage.getItem(LEGACY_STORAGE_KEY); // 兼容旧 key
    // ... JSON.parse + 字段校验
    // 旧关卡 id 乱序 → LEGACY_LEVEL_IDS 映射
    if (saved == null) saveProgress(progress); // 迁移后写回新 key
    return progress;
  } catch {
    return defaultProgress();  // 坏数据不拖垮应用
  }
}
```

**面试三点：**

1. **try/catch 兜底** —— 隐私模式/配额满/坏 JSON 不崩  
2. **schema 迁移** —— 和后端表结构迁移同构  
3. **校验字段** —— `Array.isArray`、`typeof number`，不盲目信任存储

## 12. SVG

### 12.1 是什么

**SVG = 可缩放矢量图形**，XML 格式，可以直接写在网页里：

```xml
<svg width="800" height="400">
  <circle cx="50" cy="50" r="8" fill="#2563EB" />
  <line x1="50" y1="50" x2="50" y2="114" stroke="#888" />
  <text x="70" y="55">commit a11ce01</text>
</svg>
```

- 矢量：放大不糊（对比 PNG）
- DOM 节点：可以用 JS/CSS 控制样式、事件
- 适合：图标、图表、**拓扑图/提交图**

### 12.2 为什么本项目用 SVG 而不是 Canvas / ECharts

| 方案 | 适合 | 本项目 |
|------|------|--------|
| SVG | 节点不多、要样式/事件、矢量清晰 | ✅ 提交节点几十个级 |
| Canvas | 海量粒子/游戏 | 过重 |
| ECharts/G6 | 通用图表/复杂图分析 | 布局不可控，且体积大 |

提交图是**高度定制**的领域可视化（泳道、分支签、HEAD、远程列），自研 SVG 更可控。

### 12.3 本项目怎么画

```
engine/layout.ts   计算每个节点的 (x,y)、边、泳道
components/CommitGraph.tsx   把 GraphLayout 渲染成 <svg> 节点
```

布局输出：

```ts
interface LayoutNode {
  id: CommitId;
  x: number;
  y: number;
  lane: number;
  isHead: boolean;
  branches: string[];
}
```

React 里 map 出节点：

```tsx
<svg>
  {layout.nodes.map(n => (
    <circle key={n.id} cx={n.x} cy={n.y} r={8} fill={colorForBranch(...)} />
  ))}
</svg>
```

**这也是「数据 → 视图」：** 布局函数是纯计算，组件只负责画。
